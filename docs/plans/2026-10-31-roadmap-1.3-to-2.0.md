## 3. Minor releases 1.3.0 … 1.12.0

**Order inside every version (call):**
1. Re-verify this version's ledger rows on the current SHA. 2. Write the failing tests. 3. Land the code PRs; each bug-fix label is repeated verbatim in its PR's changeset, and an observable behaviour change with no quotable contract waits behind an option until 2.0 (section 4 'Behaviour defaults' row). 4. Run the code gate (tests, build, `pnpm size`, clippy, CI) on the RC SHA. 5. Run the docs-truth lens on that SHA.
6. Rewrite docs and comments; run the docs gate on that SHA (phantom grep, link check, docs-truth lens, perf sentences, full CI), home of docs exit-gate items.
7. Merge the Version PR once its head passes CI (F23 approvals while needed); the action publishes the version commit once `ci-gate` sees CI succeed on that SHA; nothing merges to main between the Version PR merge and its publish landing (`npm view <pkg> version` equals the Version PR's version) (call); the post-cut gate checks tags and releases equal `npm view <pkg> versions --json` minus snapshot versions (`-next-`; likewise any 1.4 1:1 rerun). A post-cut pnpm install of a fresh version adds it to the scratch pnpm-workspace.yaml `minimumReleaseAgeExclude` (minimumReleaseAge 1440) or waits 24 h.

"Green CI" means the real jobs, the CI Summary depending on every job and failing on failure or cancellation.

**Pass-2 placement (call).** Items sit in the minor owning their surface (TEST_GAP in its tests, DOC_INACCURACY and STALE in its docs step); DEAD, BLOAT and STRUCTURE go to R or D, except: manifest and tarball items ride 1.4 (R and D publish nothing); a STRUCTURE fix of a BUG or PERF item goes with it; public API leaves only via 1.12 deprecation and 2.0 (D33); a false comment on unchanged code rides the earliest docs step; CI, workflow, bench-harness and docs-config items ride the version that owns that file.
